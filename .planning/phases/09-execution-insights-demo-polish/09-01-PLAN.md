# Phase 9 / Plan 09-01: V1.1 Demo Data, Docs, Smoke Tests, and Final Verification

## Objective

Make v1.1 Execution Insights repeatable to verify and demo locally. This plan extends the existing Phase 5 demo seed and smoke test so the demo starts with reviewable execution history, progress metrics, schedule explanations, and filterable task data.

## Context

- Phase 5 already added `backend/app/services/seeds/demo_data.py` and `tests/test_demo_flow.py`.
- Phase 6 added execution history and `/api/v1/execution/history`.
- Phase 7 added `/api/v1/execution/progress` and `/api/v1/execution/review`.
- Phase 8 added schedule `summary`, `risk_explanation`, `unplaced_reasons`, and task status/project filters.
- Phase 9 requirements are `REV-03` and `NFR-02`.

## Implementation Steps

### 1. Extend Demo Seeding

Update `backend/app/services/seeds/demo_data.py`.

- Keep `seed_demo_data(db, target_date=None)` repeatable and non-destructive.
- Continue to seed default energy templates, one demo project, demo tasks, one blocked time, three schedule plans, and selected balanced plan.
- Add deterministic execution history for the demo date:
  - Create at least two records through existing model semantics or a small helper local to demo seeding.
  - Include mixed statuses such as `done` and `incomplete` or `skipped`.
  - Include `actual_minutes` and `note` for at least one record.
  - Snapshot task title and estimated minutes at seed time.
- Avoid duplicate execution logs when the seed runs repeatedly for the same date and task/status combination.
- Return summary metadata such as `execution_log_count` and `review_date` in the seed result.
- Do not add destructive reset behavior in this phase.

### 2. Expand Demo Smoke Coverage

Update `tests/test_demo_flow.py`.

- Keep the isolated in-memory database fixture.
- Seed demo data twice for the same fixed date to prove repeatability.
- Confirm:
  - demo tasks, blocked time, three schedule plans, and selected balanced plan exist;
  - execution logs exist for the demo date and do not duplicate across repeated seeding;
  - `/api/v1/execution/today` returns selected work;
  - `/api/v1/execution/progress` returns planned/completed metrics;
  - `/api/v1/execution/review` returns items, actual minutes, and estimate variance;
  - `/api/v1/execution/history` returns seeded history records;
  - `/api/v1/schedules/generate` includes plan explanations and unplaced reason fields;
  - `/api/v1/ai/parse-task` still returns a structured draft;
  - every API response checked uses the success envelope.
- Keep assertions deterministic and independent of wall-clock time by passing an explicit date.

### 3. Refresh README Demo Instructions

Update `README.md` near the top.

- Keep startup instructions easy to find.
- Add a v1.1 demo section with:
  - backend setup and `alembic upgrade head`;
  - demo seed command with optional `--date YYYY-MM-DD`;
  - backend dev server command;
  - frontend install/dev/build commands from `frontend/`;
  - verification commands;
  - exact demo path: Tasks -> Calendar -> Select Plan -> Today -> Feedback -> Daily Review.
- Mention that demo seeding is repeatable and non-destructive.
- Mention that Daily Review should already show seeded execution history for the demo date.
- Preserve older planning/reference content below the quick-start area if useful.

### 4. Update GSD Completion State During Execution

When implementation passes verification:

- Add `09-01-SUMMARY.md`.
- Update `.planning/ROADMAP.md`:
  - mark Phase 9 complete;
  - mark plan `09-01` complete;
  - set progress row to `1/1 | Complete | 2026-04-29`.
- Update `.planning/REQUIREMENTS.md`:
  - mark `REV-03` and `NFR-02` complete.
- Update `.planning/STATE.md`:

  - completed phases `4/4`;
  - completed plans `7/7`;
  - next action `$gsd-verify-work` or `$gsd-complete-milestone` after successful UAT.
